# RedApp 企业分发服务设计

- 文档状态：设计基线，等待官方分发协议核验及实现验证
- 编写日期：2026-09-30
- 项目名：RedApp（Redistribution Application）
- 实现语言：Go
- 部署模型：单实例、单进程、本地持久化目录，外层反向代理负责对外 HTTPS
- 长期方向：可支持不同应用的受控二次分发
- MVP 范围：仅实现 Codex CLI 分发模块；通用底层面向固定上游 BASE_URL，不提供任意 URL 代理，也不解决 CLI 运行时连接模型 API 的问题

## 1. 目标与范围

RedApp 采用通用分发底层与静态应用模块的划分。明确不实现并行分片下载；仅对中断的单顺序下载尝试断点续传。本文的工程默认值可按部署需求调整。

### 1.1 功能要求

| 编号 | 要求 |
| --- | --- |
| R01 | 终端只能连接企业分发服务；网关可以连接上游 GitHub/OpenAI |
| R02 | 提供与官方 install.sh/install.ps1 类似的一键安装方式 |
| R03 | 本地按需缓存；不预下载某版本全部 variants |

### 1.2 非目标

- 并行分片、P2P、多节点共享缓存、分布式锁、集群高可用
- 通用 URL 代理、任意 GitHub 项目镜像、用户自选任意源站
- 多租户、外部 SSO、LDAP、外部 Redis/数据库
- 自动更新用户已安装的 Codex CLI、绕过企业的出口控制
- 无请求时完整镜像所有发行版本和所有 variants
- 第一版不要求为客户端提供任意 HTTP Range 请求；上游续传与下游 Range 是独立功能
- 不实现第二个应用、动态插件加载、通用应用配置生成器、用户可配置的任意回源规则或统一跨应用版本协议

## 2. 实现前的核验与决策边界

### 2.1 官方来源核验记录与剩余集成门禁

截至 2026-09-30，已完成下列只读来源核验：

- 当前线上 PowerShell 脚本：https://releases.openai.com/codex/install.ps1 。确认先校验 checksum manifest，再校验下载的 archive，校验后才解包
- 官方仓库 shell 脚本：https://github.com/openai/codex/blob/main/scripts/install/install.sh 。确认有等价的校验流程；尚未证明当前线上 install.sh 与该仓库版本内容完全相同
- 当前 latest 元数据：https://releases.openai.com/codex/channels/latest
- 实际版本清单样本：https://releases.openai.com/codex/releases/0.159.2/release.json 。已读取 assets.name、assets.digest、assets.browser_download_url 字段

这些核验支持“客户端会验证下载完整性”的设计前提，但不能代替对更新后的脚本及所有目标平台路径的回归测试。实现时仍须保存实际内容摘要/上游 commit 与测试样本，不能把可变 main 分支视为永久固定基线。

以下是剩余核验和固化工作，而非上述事实全部未知：

1. 固定当前线上 install.sh 的身份与仓库基线关系，穷举两种脚本的二级 URL、版本/平台分支及对应哈希校验路径
2. 基于已读取的 latest/release.json 样本固定解析契约；核对 digest 算法/编码、资源大小、相对 URL、版本字段及稳定版/预发行版的表示
3. 安装脚本是否可只通过修改下载 base URL 实现完全内网安装；是否还会访问网络辅助工具/校验文件
4. 官方实际制品下载链路是否支持 Range，重定向后是否保留请求头，是否返回稳定强 ETag
5. 官方脚本及二次分发制品的许可证、NOTICE 等随包要求

不依赖生产上游永久支持 Range。真实上游测试是可选在线集成测试，核心正确性由本地可控 HTTP 测试服务器覆盖。

### 2.2 建议工程默认值

- 服务运行于 Linux/Docker 为首要交付；客户端脚本兼容官方支持的 shell/PowerShell 平台
- SQLite 使用 WAL、短事务；应用状态与文件操作通过可恢复日志协调
- 管理页内嵌到 Go 二进制；不用 Node 作为运行依赖
- 默认不信任任何反向代理头；部署时显式配置 trusted proxy CIDR 和对外 public base URL
- HTTP 下载接口不要求管理员登录；只允许经过官方清单授权的 Codex 资源，外层企业网络可进一步限制访问
- 保留版本首次发现时间、精简的历史统计和失败事件；清理的是版本的资源文件缓存，而不是抹除审计历史
- 首版使用版本语义排序而非字符串排序；预发行版本的规则见第 8 节
- 本地文件系统持久卷；不支持 NFS/SMB 共享数据目录
- 对端读写超时、上游重试次数、日志历史上限等安全边界允许配置；实现时提供保守默认值并在配置说明中列出

### 2.3 需要明确评审的范围变更

- 官方某条实际安装路径没有完整文件哈希校验、或所需制品缺少可信哈希，需要新增校验协议/排除平台
- 官方元数据无法授权用户要求的历史版本，需要额外可信发现机制或限定可用版本范围
- 企业需要下载接口鉴权、子路径部署、多管理员或 Linux/Docker 之外的服务端支持，导致交付范围明显扩大
- 非标准版本不能无歧义地按最小版本清理；不得猜测然后删除

不改变上述目标的内部数据结构、线程调度与 UI 布局可按本设计实现。

## 3. 总体架构

请求链：客户端 → 企业反向代理 → RedApp Go HTTP 服务 → 受控上游 HTTP 客户端 → 固定配置的上游分发源。

### 3.1 最小且高价值的模块边界

底层只处理 HTTP 与文件生命周期；Codex 模块解释 Codex 协议。MVP 将 Codex 模块静态编译进同一 Go 二进制，不增加插件服务或动态加载机制。

1. Config / InstanceGuard：配置、可信代理、对外地址、OS 独占锁
2. HTTP Distributor：固定 BASE_URL 的请求构造、安全跳转、超时、响应校验和字节读取
3. DownloadManager / CacheStore：资源身份与代际、并发去重、流式多读者、续传、完整性验证、发布及回收
4. SQLiteStore / Telemetry：持久化通用缓存状态、流量与失败事件；不解释版本排序
5. AdminUI / Auth：本地登录、系统状态、缓存/任务展示与清理执行；版本信息和清理候选由 Codex 模块提供
6. Codex Module：latest/release.json 获取与解析、授权资源目录、版本比较/发现记录、安装脚本及其补丁更新流程

最小对接数据为一份经应用模块授权的资源描述：app_id、opaque_resource_key、受控上游地址、预期哈希/大小、缓存策略及展示用元数据。底层可以依赖小型结构和窄方法，不必先定义覆盖未知应用所有生命周期的庞大接口。版本清理由 Codex 模块选出资源 ID，再交给通用代际回收逻辑执行。先将 Codex 代码独立放入包；仅在实际调用边界需要时定义接口。

app_id 在 MVP 固定为 codex，仅作为低成本缓存键/数据索引命名空间；不因此提供应用创建、选择或配置功能。未来模块可复用 HTTP、缓存和管理能力，允许届时按真实需求重构。

### 3.2 固定上游与地址安全

- BASE_URL 指服务端配置的上游分发根地址，与 public base URL（终端访问 RedApp 的对外地址）是两个不同概念，配置与文档必须区分
- 普通底层路径映射严格限制在固定上游根内；终端不能传入任意 URL、切换上游或通过路径编码逃逸
- Codex 实际协议可能引用另一个官方资产主机，因此只有 Codex 模块可根据已核验清单生成额外资源地址；底层仍检查明确允许的官方 origin/CDN 跳转范围
- 固定 BASE_URL 不意味着裸露一个不经过应用授权的 catch-all 代理路由；MVP 所有可下载对象仍须满足 Codex 清单授权
- 不构建通用策略 DSL 或任意 JSON 映射引擎；当前只实现真实 Codex 协议需要的逻辑

数据库是索引与持久状态，完成缓存是否可用还必须结合文件存在性和状态。不得因为数据库标记 complete 就返回缺失或未验证的文件。

建议目录：

    cmd/redapp/
    internal/{distributor,download,cache,store,auth,httpserver,metrics,instance}/
    internal/apps/codex/
    web/
    installers/codex/upstream/
    installers/codex/patches/
    installers/codex/generated/
    scripts/update-installers.*
    docs/{design,operations,upstream-contract}.md
    Dockerfile

数据目录：

    instance.lock
    state.sqlite
    state.sqlite-wal / state.sqlite-shm
    objects/<opaque-resource-id>/<generation>.part
    objects/<opaque-resource-id>/<generation>.blob
    trash/<cleanup-id>/...

文件路径由服务生成的不透明 ID 构成，不直接拼接来自 URL 的任意路径。

## 4. Codex 元数据、授权与缓存

### 4.1 可信根与允许访问的资源

- 固定允许的官方元数据起点；客户端不得提交任意源 URL
- latest 指向具体 release；release 中的资源列表生成精确白名单
- 资源身份绑定规范化版本、官方资源标识、官方 URL 和期望哈希；若内容预期改变，应生成新资源身份
- 仅接受支持的 HTTPS 官方 origin；禁止降级 HTTP、用户信息、异常端口、localhost/私有网段等非预期目标
- 每一跳重定向都验证目的域与地址，不仅检查第一跳；仅为核验过的官方资产 CDN 提供受限允许列表
- 限制跳转次数、元数据响应大小、超时、DNS/IP 的 SSRF 风险；禁止通过路径遍历和编码别名越过清单
- HTTP 请求用户不能覆盖上游 Host、Authorization、Cookie 或代理目标
- 上游 HTTP 错误/HTML 页面不能标记为制品；验证状态码、长度、清单与最终哈希

### 4.2 latest

- 成功获取并验证后记录 fetched_at；默认 TTL=60 秒
- 有效期内直接复用；到期后的并发请求只有一个刷新任务，其余等待同一结果
- 刷新成功才能替换；失败不覆盖旧值、不延长成功获取时间
- 默认过期且刷新失败返回清晰的 502/503，不静默把旧版本当 latest；保留旧值供管理界面诊断
- 不主动后台轮询；按请求触发刷新
- 配置 TTL 改变后按原 fetched_at 与新 TTL 重新计算
- 可使用条件请求；有效的 304 可作为已重新验证的成功刷新

### 4.3 release 元数据与制品

- 验证后的版本清单长期保存，不自动过期
- 首次通过可信元数据发现版本时持久记录 first_seen_at；清理/重新下载不修改该时间
- 已知历史版本直接使用已保存清单；未知版本只通过核验过的官方固定版本查询方式发现，不能接受任意 URL
- 元数据原始响应与内部解析结果分开保存；如需要替换下载 URL，生成客户端适配响应时不得更改哈希语义
- 响应 URL 使用配置的 public base URL，避免依据不可信 Host 产生安装命令或下载链接

## 5. 单顺序回源与多客户端流式读取

### 5.1 核心模型

每个资源最多一个当前 generation。一个 generation 有一个顺序下载任务、一个增长中的本地文件、多名读者，各读者独立维护 offset。

下载器先将一块数据完整写入本地文件，确认实际写入长度，再增加 published_bytes 并广播进度。读者只读取 [0, published_bytes) 区间；追上写入进度后等待条件通知。慢客户端不阻塞下载器，也不会让快客户端等待慢者；不为每个客户端维护无限内存队列。

后到客户端从 offset=0 读已落盘部分，然后追随增长文件。下载任务不绑定第一位客户端的请求 context；所有客户端断开也可继续完成已开始的有限制品下载，便于缓存与后续请求复用。

### 5.2 状态机

资源/代际状态：

- absent：无活动缓存
- queued：已经创建唯一任务，尚未开始请求
- downloading：从上游顺序写入
- retry_wait：上游可恢复故障后等待重试，已发布前缀保持不变
- resuming：从当前有效偏移尝试 Range
- verifying：所有字节已收齐，执行最终完整哈希
- complete：哈希通过且原子发布成功
- interrupted：服务退出/达到重试限制，保留可安全续传的临时数据
- failed：不可恢复错误或无效资源
- invalid：哈希不符，所有本代数据不可再复用
- retiring：清理已摘除当前代，新请求不再绑定此代，原有读者可完成
- deleted：文件已实际回收

normal：absent → queued → downloading → verifying → complete。
恢复：downloading → retry_wait → resuming → downloading；不能安全恢复时终止当前读者并从零开始新 generation。
哈希失败：verifying → invalid → 待释放读者句柄后删除；下次请求创建新 generation。
清理可以将活动代或完成代转入 retiring，详见第 8 节。

### 5.3 流式校验的边界

本设计允许校验完成前返回数据，因此不能承诺服务端在返回第一个字节前确认完整文件正确。HTTPS 保证每段连接的传输完整性，但不替代发布清单哈希，也不能证明续传前缀与后缀属于同一内容。

响应开始后不能再把 200 改成 JSON 错误。下载/验证失败时终止未完成响应，禁止追加错误文本污染文件。若客户端已取得全部字节，其安装端哈希校验仍是最终防线。服务不能声称已收回发送出去的错误字节。

尽量在最终验证成功之前不正常结束流式响应；但不能依赖 HTTP EOF 或 Content-Length 代替安装端哈希。避免先关闭下载响应再异步验证。

可使用标准流式响应，不要求给客户端返回 Content-Length（在无法严格保证长度时不设置）；已完成文件可正常设置长度。浏览器前端和官方脚本的兼容性必须测试。

## 6. 中断与断点续传

### 6.1 持久化恢复信息

保存 bytes_on_disk、预期总长度、强 ETag/可用 Last-Modified、上游规范 URL、资源期望哈希、generation 和最近失败原因。实际文件长度是恢复偏移的依据，不能只相信可能落后的数据库计数。

启动后将遗留 downloading/resuming/verifying 归为待恢复状态。对 part 文件重新计算已有前缀的哈希状态，或者在完成后重新读完整文件验证；不尝试持久化 Go 内部哈希对象布局。

### 6.2 续传请求与验收

- 在已存在有效前缀长度 N>0 时请求 Range: bytes=N-
- 有强 ETag 则使用 If-Range；弱 ETag 不作为强一致性凭据
- 接受 206 之前验证 Content-Range 起点恰为 N、总长度与已知值一致、validator 未发生矛盾
- 即使接受续传，最终仍必须计算完整文件哈希
- 200 表示未满足续传（或资源已改变），不能追加到 part 文件
- 416 仅当已有文件恰好完整、长度合理且完整哈希通过时可完成；否则重新下载
- 格式错误、起点错误、超长/过短、内容编码导致偏移语义不明、validator 冲突一律拒绝追加
- 上游使用 Accept-Encoding: identity，并禁止透明解压打乱字节偏移
- 无可靠 validator 时可在清单固定哈希/资源身份下尝试 Range，但最终哈希承担一致性检查；绝不把未验证结果标记完成

### 6.3 失败后整文件重下

已发送给现有客户端的前缀不能撤回，所以需要从零重下时：

1. 标记旧 generation 失败并停止继续写入
2. 唤醒所有读者，结束它们的响应；客户端自行重试
3. 从当前映射摘除旧代并创建新代文件，不 truncate 仍有读者的旧文件
4. 后续请求加入唯一新代任务；旧代在句柄/租约归零后清理

不在旧响应中把新文件从零拼接到先前已发送前缀之后。网络瞬断可在有限重试期间保持读者等待；错误范围或最终哈希错误不能无限重试。

## 7. 进程独占与崩溃恢复

启动顺序：解析配置 → 规范化数据目录 → 获取排他 OS 锁 → 打开 SQLite → 恢复索引/文件状态 → 绑定服务端口。

- Linux 使用 flock 或等价的内核维护文件锁；进程持有文件描述符直到退出
- 不用“锁文件存在”判断持锁状态，不依赖 PID 文件超时，也不要求异常退出后人工删锁
- 内核在进程崩溃/被 kill 后释放锁；锁文件本身可以永久保留
- 绝不能 unlink 正在用作锁的 inode 后重建同名文件，否则会产生两个锁域
- 数据库必须位于同一独占数据目录；不支持通过另一个数据目录指向同一外部数据库
- 符号链接、路径别名按真实路径处理；对不支持可靠锁/原子 rename 的文件系统拒绝承诺单实例安全
- Docker 所有副本若挂载相同数据卷，第二个实例明确失败退出，而非等待无限时间
- 启动恢复处理“文件已 rename，但数据库未提交”和反方向的不一致；未验证文件不得恢复为 complete
- graceful shutdown 停止接收新请求，在限定时间内让读者结束/任务保存，然后释放数据库和锁

## 8. 清理与并发竞态

### 8.1 Codex 版本选择

版本含义及比较属于 Codex 模块，不设所有未来应用必须遵循 SemVer 的要求。通用清理器只接收资源 ID / generation 集合。

管理员输入最小版本，例如 0.150.0。先预览将清理的版本、文件数、逻辑占用、正在传输数量，再确认执行。版本使用语义版本比较，不用字符串或日期；默认规则是 0.150.0-rc.1 < 0.150.0，且 0.149.9 < 0.150.0。

实际官方 tag 的前缀转换规则须核验并固定。不能解析的版本不自动删除，返回明确列表；若必须处理，先明确维护策略。清理只针对选择时已存在的 generation，不设永久版本黑名单。

### 8.2 代际与租约

所有客户端读者与写入任务在 generation 上持有租约。清理与任务创建/获取在同一资源级互斥区完成线性化：

1. 记录 cleanup ID 和所选 generation 集合
2. 对每个资源持锁，将被选 generation 标记 retiring，并从“当前可取得代”映射摘除
3. 新请求在摘除之后只能创建/加入新 generation，绝不获得 retiring 文件
4. 原有客户端继续读旧代；如旧代仍回源，可完成原有服务，但不得再注册成当前缓存
5. 旧代最后一名读者和写入者释放后，实际删除文件并记账
6. 新代文件不会被此次清理删除，即使属于同一个低版本

该策略优先不打断已建立下载；代价是清理不保证磁盘空间瞬间释放，且旧代与新代短时间可以各有一次上游下载。正常并发去重的范围为同资源同当前代；明确清理/重建是例外。UI 显示“待释放空间”和“已释放空间”，不能谎称已全部释放。

清理的是资源缓存（包括遗留 part 文件），保留最小版本目录/清单授权记录、首次发现时间和必要审计数据，使新请求可按需重新获取。若未来要彻底删除审计历史，应提供不同操作。

### 8.3 崩溃与持久化删除

采用 tombstone/cleanup 记录协调数据库和文件。重启后 retiring 代已无旧进程读者，可按记录继续回收。文件不存在则幂等地完成删除；不能只凭相同路径删除新代。进程内与持久层统一使用 generation ID，避免 ABA 竞态。

磁盘统计需包括 complete、part、retiring、SQLite/WAL 与其它服务文件；每项分类显示，避免只计算可见完成制品而低估占用。

## 9. SQLite 数据模型

建议表：

- settings(key, value, updated_at)：latest TTL 等非秘密动态设置
- admins(id, password_hash, credential_version, created_at, updated_at)
- versions(id, app_id, canonical_version, upstream_tag, first_seen_at, release_digest, metadata_status)
- metadata_cache(app_id, key, source_url, body, etag, fetched_at, validated_at)
- artifacts(id, app_id, version_id, name, source_url, expected_hash, hash_algorithm, expected_size, current_generation_id)
- generations(id, artifact_id, state, path, bytes_on_disk, total_bytes, etag, started_at, upstream_completed_at, finished_at, download_duration_ns, verification_duration_ns, source_bytes, resume_count, retired_at)
- events(id, type, artifact_id, generation_id, occurred_at, category, status_code, safe_message)
- cleanup_jobs(id, minimum_version, state, started_at, finished_at, pending_bytes, freed_bytes)
- counters(bucket, dimension, value)：按需持久聚合，不为每个下载字节写数据库

约束与索引：资源授权身份在 app_id 内唯一；版本规范名在 app_id 内唯一，MVP 的 app_id 固定为 codex；artifacts.current_generation_id 是唯一的当前可取得代指针（可为 NULL），以外键及同资源归属检查确保指向本资源 generation；更新/摘除指针在短事务内完成。应用资源锁协调文件与读者，数据库指针避免仅靠口头约定维持“最多一个当前代”。SQLite 不持有跨网络请求的事务。使用 schema 版本迁移，备份和恢复说明包含 WAL；不得以直接复制活跃单个 sqlite 文件作为一致备份。

哈希通过后 fsync/close 临时文件、同文件系统原子 rename，再完成数据库提交；故障时启动恢复核对。明确不同平台的持久性差异，测试故障窗口。

## 10. 管理界面、安全与反向代理

### 10.1 初次启动及登录

- 仅在数据库中不存在管理员时，用 crypto/rand 生成高熵随机密码，明文只在首次初始化日志输出一次
- 数据库只保存经成熟密码 KDF 处理的 hash，不保存明文密码
- 重启不重新生成/再次打印；日志说明立即登录修改密码并保护初始化日志
- 会话 Cookie 使用 HttpOnly、SameSite、适当的 Secure；密码修改使旧会话失效
- 登录限速、错误消息不泄漏细节；修改配置/密码/清理都要求登录与 CSRF 防护
- 管理员鉴权不等同于限制下载资源；资源路由由白名单限制能力，企业访问范围由网络与反代控制

### 10.2 反代头

只对 RemoteAddr 命中 trusted proxy CIDR 的连接解析 Forwarded / X-Forwarded-*。不可信连接提交这些头时忽略。运维建议反代覆盖外部传入头，不盲目 append 未验证值。

支持 RFC Forwarded 的 for/proto/host 与必要的引用、IPv6 格式；对于多跳链从最近可信代理向外逐个剥离，停在首个不可信节点。避免简单取最左端 IP。上述从右到左算法仅用于 client IP 识别，不能直接套用于 host/proto。host/proto 优先使用配置的 public base URL；需要从头部取得时，仅接受显式约定的可信入口代理负责设置的那一项，并要求该入口覆盖用户原始 host/proto 转发值，不能从链中任挑一项。Forwarded 存在且合法时优先使用；与 X-Forwarded-* 冲突时采用固定且记录在文档中的策略，不拼接两个链。畸形头拒绝作为可信值。

public base URL 是生成脚本命令和下载链接的首选来源。即使代理可信，也不无限信任任意 Host；配置主机允许列表。HTTPS 终止在代理后正确设置安全 Cookie 和绝对链接；服务端口不对不受控网络直接暴露。

### 10.3 页面与指标

- 仪表盘：版本/构建信息、启动时间、OS/架构、Go 版本、进程内存/线程或 goroutine、活动下载/客户端
- 磁盘：服务实际占用、可见缓存、临时/待清理占用、数据目录所在文件系统可用空间
- 流量：当前上游接收/下游发送 B/s、累计字节；注明进程生命周期统计与持久历史统计的区别
- 访问：总请求、制品请求、缓存命中、未命中、共享回源跟随者、成功/失败；健康探针不污染业务访问
- 版本历史：first_seen_at、资源个数、当前缓存量、状态，点击进入资源列表
- 资源详情：大小、已写入字节、状态、开始/完成时间、平均/当前回源速度、续传次数、最近错误、校验结果
- 失败历史：发生时间、资源、上游状态码、错误分类（DNS/TLS/超时/长度/Range/磁盘/哈希等）、安全摘要
- 设置：修改密码、latest TTL；清理预览、执行和结果

速度定义：活动实时速度采用最近短窗口（建议 5 秒）的上游实际读取字节差/时间；响应附采样时间。已缓存平均速度=最终文件大小/该成功 generation 从回源开始到上游数据接收完成的耗时，包含中断、重试与退避等待，不包含最终哈希验证耗时。另行记录验证耗时；如展示累计实际接收字节计算的链路吞吐，使用不同名称，不能与文件平均下载速度混用。同时显示最终文件大小和下载耗时，避免续传/重试让指标含义不清。页面手动刷新或低频轮询即可。

失败日志必须删去敏感 query/token、Cookie、密码；上游带签名 CDN URL 不作为永久公开链接。事件历史应有有界保留（建议时间/条数两重限制）以免磁盘无限增长；制品长期缓存策略不等同于日志永久保留。

## 11. 官方安装脚本维护

保持 upstream 原文、上游来源/commit/hash、局部 patch 与生成结果分离：

1. update-installers 命令仅从固定官方来源获取到临时目录
2. 记录上游版本/commit/内容 hash；检查许可证及换行
3. 对上游原文执行严格 patch；不使用忽略错误或静默宽松 fallback
4. 补丁冲突时非零退出，保留已发布脚本，不自动猜测合并
5. 对生成脚本进行语法检查、离线测试和全 URL 访问检查
6. 人工 review 新版 upstream diff 与 patch 后随应用发布

补丁尽量只调整下载 base URL、必要元数据定位及企业错误提示，保留官方平台识别、安装位置、校验、解包等逻辑。若官方新增 URL/资源未覆盖，测试失败而非让终端意外连接公网。通过同源固定路由动态提供或构建时生成脚本时，所有替换值严格校验/转义，不能形成 shell/PowerShell 注入。

测试至少覆盖：被篡改制品必须安装失败；支持的平台/variants；显式版本/latest；代理后 URL；shell 与 PowerShell；补丁无法应用；终端仅允许访问本服务时仍能安装。安装脚本不自动配置 CLI API endpoint 或凭据。

## 12. Docker 与运维

- 多阶段构建 Go 二进制与前端静态资源；运行镜像不依赖 Node/数据库服务
- 非 root 用户、明确数据卷位置、只读根文件系统兼容、可写路径仅数据目录/必要临时目录
- 镜像包含 HTTPS 根证书与正确时间处理能力；不关闭上游 TLS 验证
- SQLite 驱动优先评估纯 Go 实现；若采用 CGO，显式固定构建/运行库并验证镜像兼容性
- 暴露单 HTTP 端口给反向代理；public base URL / trusted proxies 通过配置提供
- liveness 不因上游不可用失败；readiness 检查初始化与本地存储可用性，不要求外网即时成功
- 正常 SIGTERM 与强制 SIGKILL 重启均测试；卷空间不足时返回清晰错误并不中毒已有完成缓存
- 外部镜像发布及云资源配置不属于服务自身职责

## 13. 验收测试矩阵

| 测试 | 验收标准 |
| --- | --- |
| A01 按需回源 | 只请求一个 variant 时其它制品不下载 |
| A02 100 并发 | 同资源同代 100 个并发请求仅 1 次完整上游任务；所有客户端字节相同 |
| A03 流式共享 | 文件尚未收齐时多个客户端已收到前缀；晚到者能读取前缀后追随 |
| A04 慢读者 | 慢客户端不拖慢回源/快客户端；内存不随文件大小或读者落后无限增长 |
| A05 最终哈希 | 错误哈希使本代失效，后续请求重新回源；安装脚本拒绝错误文件 |
| A06 正常续传 | 上游中断后只请求剩余 range，206 范围正确，完整哈希通过 |
| A07 不支持续传 | 上游返回 200 时绝不追加；旧响应结束，新代从 0 重下 |
| A08 非法续传 | 错误 Content-Range、validator 变更、416、编码/长度错误均按设计处理 |
| A09 重启恢复 | SIGKILL 后可立刻重启获得锁，安全恢复 part，完成后验证正确 |
| A10 双实例 | 同一数据卷第二进程拒绝启动；路径别名不能绕开独占 |
| A11 latest TTL | 60 秒内复用；超时并发仅刷新一次；失败不延长旧值有效期；配置修改有效 |
| A12 永久缓存 | release/制品不因时间流逝重新下载；清理后才重新按需获取 |
| A13 白名单 | 任意 URL、路径遍历、伪造资源、非允许重定向、私网目标均不可用于代理 |
| A14 清理竞态 | 读取/写入/新请求/清理交错，旧代可完成，新代不被删除，磁盘最终正确回收 |
| A15 清理崩溃 | 删除各故障窗口重启均幂等恢复，无新代误删，无 dangling complete |
| A16 版本边界 | 稳定/预发行/前缀按语义比较；非法最小版本拒绝，不可解析版本不误删 |
| A17 管理安全 | 初次密码一次性日志、密码 hash、改密注销旧会话、CSRF/限速有效 |
| A18 代理安全 | 不可信 Forwarded 被忽略；可信多跳/IPv6/proto/host 正确且不可注入 |
| A19 指标 | 两名下游共享一个上游时字节分别记账；速度定义、采样时间与磁盘分类正确 |
| A20 脚本更新 | patch 冲突失败且不覆盖成品；坏 hash 安装失败；无额外终端外网请求 |
| A21 Docker | 干净机器仅 Docker 可运行；卷持久化、非 root、证书、健康检查和重启正常 |
| A22 资源边界 | 磁盘满、过多客户端、源站挂起、数据库 busy 均有界失败，无死锁 |
| A23 故障恢复 | 文件发布与数据库事务之间的崩溃不把未经校验的数据恢复为可用 |
| A24 架构边界 | 通用下载/缓存包不解析 Codex release.json 或 SemVer；MVP 只有静态 Codex 模块，固定 BASE_URL 不能被请求覆盖为任意目标 |

测试层级：纯单元（清单/版本/代理头/状态机）、可控 HTTP 集成、文件系统/进程故障注入、Docker 冒烟、可选真实上游兼容性测试。执行 Go race detector；对清理/请求交错使用 barrier 控制，而非仅靠 sleep 随机碰撞。
