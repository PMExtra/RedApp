# 0001：1.0 前允许不兼容变更，合理成本下提供迁移

## 背景

原文将“1.0 前允许 breaking changes”错误收紧为“不允许迁移”，并假定没有真实部署。已有数据需要保护时，这一表述不成立。允许放弃兼容不等于禁止平滑升级。

## 决定

- **1.0 之前**：不强制兼容所有历史 schema；能够以合理成本保留数据时应提供明确范围的迁移。无法合理支持的版本可只读拒绝，说明限制，不默认为用户接受删除数据。
- 每次 schema 变化提升 `SchemaVersion`；迁移范围由 `MinimumMigratableVersion` 和连续步骤明确表示，`0` 表示当前无迁移支持。
- 当前支持 schema 15→16；更早版本不在本次支持范围。两张表扩展 CHECK 与配置列，增加刷新状态表，不改变 blob 布局。
- 复用迁移前备份、事务、外键校验和全新 schema 比对；所有支持的旧版本保留 golden fixture，验证旧数据保留、失败回滚和重启。任何迁移都不直接操作 blob 文件。
- **1.0 起**：每次 schema 变化必须附带迁移与 golden fixture 测试；不因进入 1.0 自动截断已有迁移范围。
- 降级不属于升级迁移承诺。回退使用对应旧二进制和升级前的一致备份；不能把旧二进制直接指向升级后的数据库。

## 后果

兼容窗口由实际成本和数据风险决定，不承诺所有历史 schema。升级说明必须写明支持范围、备份与空间需求、回退限制。技术流程见 [development.md](../development.md#schema-迁移)。
