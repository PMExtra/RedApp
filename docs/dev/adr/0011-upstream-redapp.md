# 0011：应用级上游 RedApp

## 背景

企业常见多级部署：外网实例能访问官方，内网实例只能访问外网实例。RedApp 的分发路径与官方发布布局兼容，下游把来源地址指向上游应用即可串联，但展示信息要手工复制，JSON 发布要手写 jq；http-cache 对下游返回 `no-store`，Codex 校验依赖上游的公共地址，串联并不可靠。完整设计与实施切分见 [#22](https://github.com/PMExtra/RedApp/issues/22)。

## 决定

- 不重构 Provider。镜像应用是普通本地应用，记录绑定的上游实例和远端 `vendor/app`；Provider 由上游决定（hosted 映射为 http-cache），来源配置由绑定推导，不可编辑。远端以 key 识别，上游删除后同名重建视为同一应用。
- 名称、说明、图标和使用说明以上游快照作为模板层，复用模板 + 稀疏覆盖，可按语言覆盖与恢复跟随；分类、Tag 和运维策略属于本地。
- 只向所选上游请求，不回退官方；上游新增的应用不自动引入。RedApp 公开访问，不引入凭证或授权模型。
- 每跳沿用现有流式核心：边下边读，校验通过才发布缓存，失败中断连接且不留缓存。
- 上游请求携带 `Via: redapp/<instance_id>`，见到自身标识即拒绝，防止环路。
- 每个绑定只有一个上游；发布类应用的多上游回落待有需求再做。

## 后果

- 新增上游表、绑定字段和公开的 mirror 描述接口，schema 递增；现有应用行为不变。
- 补齐的串联缺口同样惠及手工配置的下游。
- 上游不可达时沿用现有的缓存与快照行为；离线期间无法得知上游变化。
